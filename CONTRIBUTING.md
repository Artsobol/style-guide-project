# Внесение изменений

Предлагайте изменения через отдельную ветку и Pull Request.
До редактирования прочитайте `docs/guide/` и определите, какие документы и правила затрагивает изменение.

## Локальная подготовка и проверки

Установите Python 3.12, Node.js 22+ и npm. Из корня репозитория создайте и активируйте окружение:

```bash
python -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements.txt
npm ci
```

В PowerShell активируйте окружение командой `.venv\Scripts\Activate.ps1` вместо `source`.

```bash
npm run lint:md
python scripts/check_examples.py
mkdocs build --strict
mkdocs serve
```

Просмотрите изменённые страницы в браузере, в том числе ссылки, код и таблицы.
Остановите сервер сочетанием Ctrl+C.

## Ветки и коммиты

Создавайте `docs/<краткая-тема>`, `fix/<краткая-тема>` или `chore/<краткая-тема>` от актуальной `main`.
Для лабораторного раздела используется `docs/accessibility`.

```bash
git switch main
git pull --ff-only
git switch -c docs/new-section
```

Используйте Conventional Commits: `<type>(<scope>): <описание>`.
Допустимы `docs`, `fix`, `chore`, `ci`; scope необязателен.
Примеры: `docs(api): clarify title constraints`, `ci: validate documentation before deploy`.
Один коммит должен решать одну связанную задачу. Исключите секреты и каталог `site/`.

## Добавление раздела

1. Создайте файл с именем в нижнем регистре через дефисы в `docs/guide/`.
2. Добавьте один H1, вводный абзац, правила с идентификаторами и проверяемые примеры.
3. Добавьте относительный путь в `nav` файла `mkdocs.yml`.
4. Обновите связанные ссылки и при существенном изменении `CHANGELOG.md`.
5. Выполните проверки и проверьте страницу в локальном браузере.
6. Создайте коммит, отправьте ветку и откройте PR в `main`.

## Pull Request и ревью

В описании укажите проблему читателя, изменения, затронутые правила и результаты проверок.
Используйте шаблон PR. Дождитесь зелёных проверок и независимого содержательного ревью.
Рецензент сверяет контракт, термины, примеры, доступность и достаточность действий при ошибке.
Каждое замечание привязывает к фрагменту и, если применимо, идентификатору правила.

Автор отвечает на все замечания и вносит исправления новым коммитом.
Если предложение не принято, автор объясняет причину; рецензент подтверждает решение.
Сопровождающий сливает PR после одобрения и проверяет результат публикации.
Для лабораторной требуется реальный обмен PR с другим студентом и три комментария в PR партнёра.
Автоматическая проверка и помощь ИИ не заменяют эту часть.

## Публикация

После merge в `main` тот же workflow повторно проверяет проект, собирает артефакт и публикует Pages.
Сопровождающий проверяет зелёный job `deploy` и открывает изменённую страницу на сайте.
Рекомендуется включить защиту `main` с обязательным ревью и проверкой `validate` через настройки GitHub.
Эти настройки требуют прав владельца и не задаются одним файлом в репозитории.
