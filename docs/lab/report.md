# Лабораторная работа № 3

Тема: стайлгайд технической документации REST API на Java и Spring Boot.
Цель: пройти цикл Docs as Code от проектирования правил до проверки и публикации документации.

## 1. Изучение теории

По материалам «Стайл-гайд1.pptx» руководство по стилю объединяет требования к языку,
терминам, структуре и оформлению. Оно снижает разнобой между авторами и упрощает сопровождение.
Работу следует начинать с аудитории и существующих документов, затем определить правила,
проверить их на примерах и поддерживать через процесс внесения изменений.

В Google Developer Documentation Style Guide изучены назначение руководства и приоритет правил проекта.
Для этого проекта принят такой же порядок: локальные правила, затем внешние рекомендации.
Русский язык и примеры Spring определяются потребностями нашей аудитории.
Ссылка Ozon из презентации сохранена в источниках, однако её содержимое при подготовке не удалось получить.
Выводы о конкретных правилах Ozon поэтому не делаются.

Для HTTP-ошибок изучен RFC 9457, для Spring — документация `ProblemDetail`.
Это технические источники формата данных; редакционные решения проекта сформулированы отдельно.
Ссылки и назначение каждого источника приведены в [библиографии](../references.md).

## 2. Ответы на вопросы

### 2.1. Нужны ли стайлгайды

Да, если документацию пишут несколько авторов, документы регулярно обновляют или читатель
использует их для интеграции с API. Единый порядок полей и ошибок сокращает время поиска.
Например, обязательная таблица параметров предотвращает пропуск ограничения длины `title`.

Отдельный объёмный документ нужен не всегда. Для одноразовой заметки достаточно короткого шаблона.
Затраты на согласование и сопровождение должны соответствовать риску ошибок.
Даже небольшой API выигрывает от минимального набора: словарь, структура операции и проверка примеров.

### 2.2. Применение при разработке документации

Автор начинает с шаблона операции, заполняет авторизацию, ограничения, успешный ответ и ошибки.
Редактор проверяет термины по словарю, а CI проверяет Markdown и собирает сайт.
Например, фразу «дерните ручку» заменяют на «Выполните запрос», а ответ `400` дополняют
конкретным действием: «Укажите title длиной от 1 до 120 символов».
При изменении DTO разработчик одновременно обновляет таблицу полей, JSON и OpenAPI.

### 2.3. Применение искусственного интеллекта

ИИ может предложить структуру, найти неодинаковые термины, подготовить черновик примера,
сопоставить текст с чек-листом и предложить понятную формулировку ошибки.
На вход передают утверждённый словарь, контракт и обезличенные данные.
Секреты и данные пользователей в запросы к ИИ не включают.

Ответственный автор проверяет факты, HTTP-семантику, ссылки и воспроизводимость.
ИИ не подтверждает работу сервера и не заменяет ревью другого студента.
В этой работе ИИ использован для подготовки текста, конфигурации и самопроверки.
Взаимное студенческое ревью не заявляется как выполненное.

## 3. Объект стайлгайда

Объект: внешняя техническая документация учебного Task API на Java и Spring Boot.
Основные читатели — разработчики интеграций с базовыми знаниями HTTP и JSON.
Вторичные читатели — тестировщики и технические писатели.
Им нужно выполнить первый запрос, найти ограничения и восстановиться после ошибки.

В область входят обзор, быстрый старт, справочник операций, примеры, ошибки и журнал изменений.
Соглашения о Java-коде рассматриваются только в примерах документации.
Архитектура приложения и полное руководство по программированию Java находятся вне области.
Версия Spring не предполагается установленной у читателя: пример `ProblemDetail` требует Spring Framework 6+.

## 4. Разработка стайлгайда

### 4.1. Структура правил

Каждое правило имеет идентификатор, проверяемое требование и пример либо критерий приёмки.
«Обязательно» означает требование для принятия PR. «Рекомендуется» допускает обоснованное отклонение.
Исключение фиксируют в PR с причиной и затронутыми документами.

| Вопрос автора | Группа правил | Критерий проверки |
| --- | --- | --- |
| Для кого и о чём текст? | S — область | Указаны аудитория, задача и версия |
| Как назвать действие и сущность? | L — язык | Термины соответствуют словарю |
| Какие сведения обязательны? | D — структура | Есть условия, шаги, результат и ошибки |
| Как оформить пример и таблицу? | F — формат | Есть язык кода, заголовки и подписи |
| Как описать контракт REST? | A — API | Типы, ограничения и статусы совпадают |
| Как поддерживать актуальность? | Q — качество | Есть проверки и процесс изменения |

### 4.2. Правила

Правила записаны полностью в разделе «Руководство по стилю» и имеют идентификаторы S01–Q04.
Например, A02 требует явно различать отсутствие поля и `null`, F02 — обозначать язык кода,
а L03 — раскрывать сокращение при первом употреблении.
Такая запись позволяет сослаться в ревью на конкретное требование.

### 4.3. Структура стайлгайда

1. Область применения и приоритет требований.
2. Язык, тон и словарь терминов.
3. Шаблоны и структура документов.
4. Правила Markdown и оформления.
5. Правила REST API, ошибок и примеров Java.
6. Контроль качества и сопровождение.

Раздел доступности добавляется отдельным коммитом в ветке `docs/accessibility`,
чтобы выполнить пункт 11 и представить изменение для реального ревью.
