# Проверка стайлгайда на двух документах

## 5. Метод проверки

Для испытания написаны [первый запрос](../examples/quickstart.md)
и [справочник создания задачи](../examples/create-task.md).
Оба используют один контракт Task API 1.0.0. Оценка выполнена авторской самопроверкой.
Она не является независимым пользовательским испытанием или взаимным студенческим ревью.

## Применение правил

| Проверка | Первый запрос | Справочник | Основание |
| --- | --- | --- | --- |
| S01: версия и цель | Указаны во введении | Указаны во введении | Контракт 1.0.0 |
| L01–L03: тон и словарь | Действия «задайте», «создайте» | Термины из словаря | Нет жаргона «ручка» |
| D02: условия и результат | Bash, curl, токен, `201` | Ссылка на условия | Ожидаемый результат явный |
| D03: структура операции | Ссылка на справочник | Все обязательные разделы | Нет параметров пути и query |
| F02: код | `bash`, `json` | `bash`, `http`, `json` | JSON разбирается парсером |
| A02: ограничения | Вынесены в справочник | Обязательность, `null`, длина | Таблица согласована с контрактом |
| A03: ошибки | Причина и действие | Статусы и Problem Details | Проверяемый JSON ошибки |
| A04: токены и повторы | Ввод без эха, предупреждение | Переменные и риск повтора | Нет действительного секрета |
| Q01: автоматизация | Линтер и сборка | Линтер, сборка, проверка данных | Команды воспроизводимы |

## Замечания, найденные при разработке

| Проблема раннего варианта | Уточнение правила | Применённое исправление |
| --- | --- | --- |
| «120 символов» неоднозначно для Java | A02 требует модель длины | Указаны кодовые единицы UTF-16 |
| Демоадрес можно принять за стенд | A04 требует маркировать `.example` | Введено явное условие о сервере |
| Повтор POST мог создать дубль | A04 требует описать повтор | Добавлено предупреждение в оба текста |
| Формат ошибки не объяснял поля | A03 требует описание | Добавлены значения пяти полей |

Это саморедактирование; замечания не приписываются другому студенту.

## Оценка качества

Стайлгайд применим к двум разным жанрам: он задаёт порядок сведений и позволяет проверить
ограничения поля без устной договорённости. Идентификаторы правил делают замечания конкретными.
При этом испытание охватывает только одну POST-операцию. Не проверены документация пагинации,
загрузка файлов, пользовательская понятность и совместимость с реальным сервером.

Критерии следующего этапа: независимый читатель выполняет первый запрос на стенде,
рецензент проверяет все ограничения по контракту, а замечания фиксируются в настоящем PR.
Результат локальной сборки и перечень оставшихся действий записаны в корневом `STATUS.md`.
