# REST API и примеры Java

## A01. Метод, путь и версия

Обязательно пишите метод прописными буквами: `POST /api/v1/tasks`.
Разделяйте базовый URL и путь. В учебном контракте коллекции названы существительными во множественном числе.
Это соглашение проекта, а не требование HTTP. Версию пути и несовместимые изменения описывайте явно.
Для каждой операции укажите права и побочные эффекты.

## A02. Поля и ограничения

Обязательно перечисляйте тип, обязательность, допустимость `null`, диапазон, формат и пример значения.
Отсутствие поля и явное значение `null` описывайте отдельно.
Для строки определите, учитываются ли пробелы и как измеряется длина.
Пример: `title` обязателен, не допускает `null`, не может состоять только из пробелов,
длина от 1 до 120 кодовых единиц UTF-16 до обрезки. Это соответствует выбранной модели Java `String`.
Не объявляйте ограничение «120 символов Unicode» без уточнения модели подсчёта.

## A03. Ответы и ошибки

Обязательно покажите статус, значимые заголовки и тело успешного ответа.
Если тела нет, обозначьте это; для `204` не приводите JSON.
Для создания ресурса учебный контракт использует `201` и `Location`.
Ошибки представляются как `application/problem+json` по [RFC 9457](../references.md).

В проекте обязательны поля `type`, `title`, `status`, `detail`, `instance`.
Это локальное требование: RFC допускает отсутствие отдельных членов.
`title` описывает тип проблемы, `detail` - конкретное исправление.
Для `type: about:blank` используйте стандартную фразу HTTP-статуса, например `Bad Request`.
Не раскрывайте стек, SQL, токен или персональные данные.
Для каждого статуса перечислите причину и действие клиента.

## A04. Безопасные и воспроизводимые запросы

Обязательно обозначайте демонстрационные адреса через домен `.example`, а реальные адреса - через переменные окружения.
Токен берите из `TOKEN`; не публикуйте действительные секреты.
Показывайте необходимые заголовки и полное минимальное тело.
Не предлагайте отключить TLS-проверку. Для POST укажите риск повторного создания при повторе запроса.
Если сервер не реализует идемпотентный ключ, не обещайте идемпотентность.

## A05. Согласованность Java и контракта

Пример Java обязан указывать контекст и минимальную совместимую технологию.
Не выдавайте фрагмент за запускаемое приложение.
Следующий фрагмент требует Spring Framework 6+ (например, в совместимой версии Spring Boot)
и иллюстрирует создание ошибки внутри обработчика Spring MVC:

```java
import org.springframework.http.HttpStatus;
import org.springframework.http.ProblemDetail;

ProblemDetail problem = ProblemDetail.forStatusAndDetail(
    HttpStatus.BAD_REQUEST,
    "Укажите title длиной от 1 до 120 символов"
);
problem.setTitle("Bad Request");
```

Для полного ответа обработчик также согласует `instance`, статус и тип содержимого с контрактом.
Сверяйте JSON, OpenAPI, DTO и таблицу полей в одном изменении.
Примеры этого репозитория проходят проверку данных; Java-фрагмент здесь не компилируется.
