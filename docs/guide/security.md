# Безопасность документации и примеров API

Раздел устанавливает правила безопасной публикации технической документации REST API.
Он дополняет правило A04 и применяется к тексту, командам, JSON-примерам,
OpenAPI и сообщениям об ошибках.

## SEC01. Секреты и токены

Никогда не публикуйте действительные токены, пароли, ключи и cookies в Markdown,
JSON, OpenAPI, истории команд или Pull Request.

В командах используйте переменные окружения или условные обозначения:

```bash
export TOKEN='значение только для локального сеанса'
```

В документации передавайте токен как `${TOKEN}` или `<токен>`. После работы удалите секрет из текущей оболочки:

```bash
unset TOKEN
```

Если секрет случайно попал в репозиторий, одной правки файла недостаточно:
сообщите владельцу секрета и выполните процедуру его отзыва и замены.

## SEC02. Авторизация и права

Для каждой защищённой операции обязательно укажите способ авторизации, заголовок, требуемое право и поведение при отказе.

Для учебного Task API запрос создания задачи использует Bearer-токен и право `tasks:write`:

```http
Authorization: Bearer <токен>
```

Не называйте токен паролем или ключом, если контракт использует
Bearer-авторизацию. Не включайте секрет в URL, query-параметры или тело запроса.

## SEC03. Безопасные адреса и транспорт

Для демонстрационных запросов используйте домены `.example`. Реальный адрес стенда передавайте через переменную `BASE_URL`:

```bash
export BASE_URL='https://api.example'
```

Не публикуйте внутренние IP-адреса, имена хостов, адреса баз данных и служебные
URL без разрешения владельца системы. Не предлагайте отключать проверку TLS или
использовать небезопасный HTTP для защищённых данных.

## SEC04. Данные в примерах

Используйте вымышленные и минимальные данные. Не публикуйте персональные данные,
реальные идентификаторы пользователей, платёжные сведения и содержимое
производственных запросов.

Перед публикацией проверьте не только отображаемый текст, но и вложения,
JSON-файлы, скриншоты и историю коммитов. Пример должен показывать необходимую
структуру запроса, а не реальные данные.

## SEC05. Безопасные сообщения об ошибках

Сообщение об ошибке должно помочь исправить запрос, но не раскрывать внутреннее
устройство сервера. Для API используйте согласованный тип
`application/problem+json` и описывайте действие клиента.

Допустимый пример:

```json
{
  "type": "about:blank",
  "title": "Bad Request",
  "status": 400,
  "detail": "Укажите title длиной от 1 до 120 символов",
  "instance": "/api/v1/tasks"
}
```

Не включайте в ответ stack trace, SQL-запросы, имена файлов, токены, секретные
заголовки и персональные данные. Различайте причину, видимую клиенту, и
внутренние диагностические сведения сервера.

## SEC06. Повторные изменяющие запросы

Для операции, изменяющей данные, обязательно укажите последствия повтора.
В учебном контракте повторный `POST /api/v1/tasks` может создать
дополнительную задачу.

Не обещайте идемпотентность, если контракт не описывает идемпотентный ключ или
другое средство защиты от повторного создания. При обрыве соединения сначала
предложите проверить результат операции, а не повторять `POST` вслепую.

## SEC07. Проверка перед Pull Request

Перед созданием Pull Request автор обязан проверить:

- в документации нет действительных токенов, паролей и ключей;
- секреты не записаны в URL, query-параметры или JSON-примеры;
- демонстрационные адреса используют `.example`, а реальные адреса задаются переменными;
- в примерах нет персональных и производственных данных;
- сообщения об ошибках не раскрывают stack trace, SQL и внутренние пути;
- для защищённых операций указаны схема авторизации и права;
- для повторных `POST` описаны последствия и отсутствие идемпотентности;
- выполнены `npm run lint:md`, `python scripts/check_examples.py` и `mkdocs build --strict`.

Эта проверка снижает риск публикации секрета, но не заменяет отзыв уже
скомпрометированного учётного материала и содержательное ревью.
