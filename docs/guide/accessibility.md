# Доступность текста

Раздел помогает сделать документацию понятной и пригодной для чтения с клавиатуры,
экранным диктором и при увеличении масштаба. Ориентир - WCAG 2.2 уровня AA.
Перечень правил и успешная сборка сами по себе не подтверждают соответствие сайта WCAG.

## X01. Понятные инструкции

Обязательно пишите короткие предложения с конкретным действием и явно названным объектом.
Раскрывайте предметные сокращения при первом употреблении. Избегайте выражений,
которые требуют культурного контекста, и слов «просто», «очевидно».

Пример: «Передайте токен в заголовке Authorization» вместо «Авторизуйтесь привычным способом».
Если операция требует предварительных знаний, дайте ссылку на объяснение перед первым шагом.

## X02. Семантическая структура

Обязательно используйте заголовки по порядку и списки по назначению.
В основном содержимом каждой страницы должен быть один H1.
Учитывайте заголовок, который может добавлять тема MkDocs: после сборки проверьте HTML,
чтобы заголовок из Markdown не дублировал автоматически созданный H1 в содержимом.
Не оформляйте смысловой заголовок только жирным шрифтом.
Перед длинным примером объясните его цель; после него укажите ожидаемый результат.
Проверка: по списку заголовков можно понять устройство документа без чтения всех абзацев.

## X03. Ссылки и альтернативный текст

Обязательно называйте назначение ссылки: «Ограничения поля title», а не «здесь».
Для информативного изображения укажите alt-текст, передающий его смысл в контексте.
Сложную схему дополните текстовым описанием связей.
Для чисто декоративного изображения используйте пустой alt-текст.
Не включайте в alt-текст слова «картинка» и не повторяйте соседнюю подпись без необходимости.

## X04. Независимость от цвета и расположения

Обязательно обозначайте статус и предупреждение текстом.
Пишите «Ответ 400: неверный title», а не «Ошибка показана красным».
Заменяйте «нажмите кнопку справа» на название элемента.
Если автор меняет цвета темы, проверьте контраст текста и фона по
[WCAG 2.2, 1.4.3 (уровень AA)](https://www.w3.org/TR/WCAG22/#contrast-minimum):
не менее 4,5:1 для обычного текста и 3:1 для крупного.
Крупным считается текст размером не менее 18 pt (24 CSS-пикселя)
либо не менее 14 pt (примерно 18,67 CSS-пикселя) при полужирном начертании.
Для текста CJK учитывайте эквивалентный размер, указанный в определении WCAG.
Исключения для логотипов, декоративного текста и неактивных элементов приведены в критерии.
Отдельный, более строгий
[критерий 1.4.6 (уровень AAA)](https://www.w3.org/TR/WCAG22/#contrast-enhanced)
задаёт пороги 7:1 и 4,5:1 соответственно; он не входит в выбранный ориентир уровня AA.

## X05. Таблицы и код

Обязательно задавайте таблицам строку или столбец заголовочных ячеек.
После сборки эти ячейки должны быть размечены элементами `<th>`;
для явной связи с данными используйте `scope="col"` или `scope="row"` по направлению заголовка.
Обычная подпись над таблицей не заменяет заголовочные ячейки.
Для простых Markdown-таблиц используйте первую строку как заголовочную и проверьте полученный HTML.
Если нужна разметка заголовков строк, используйте HTML-таблицу с `<th scope="row">`.
Избегайте объединённых ячеек.
Длинные пояснения переносите в обычные абзацы рядом с таблицей.
Команды и JSON публикуйте текстом, доступным для копирования, с обозначением языка.
Не включайте номера строк и приглашение оболочки в копируемую команду.
Проверяйте горизонтальную прокрутку длинного кода на узком экране.

## X06. Ошибки и восстановление

Обязательно указывайте причину ошибки и конкретное действие читателя.
Не обвиняйте пользователя. Пример: «Укажите title длиной от 1 до 120 символов»
вместо «Вы ввели неправильные данные».
Если действие может создать дубль или удалить данные, объясните последствие до команды.
Не требуйте определять ошибку только по цвету, значку или звуку.

## X07. Ручная приёмка страницы

Перед одобрением изменений, влияющих на отображение, рецензент проверяет:

1. Переход по ссылкам, меню и поиску клавишами Tab и Shift+Tab; отсутствие ловушки фокуса.
   Активацию ссылок клавишей Enter, а кнопок - Enter и Space.
2. Видимость фокуса, возможность перейти к основному содержимому.
3. Чтение заголовков и ссылок экранным диктором; логичный порядок и понятные названия.
4. Увеличение текста до 200% без потери содержимого и функций по
   [критерию 1.4.4](https://www.w3.org/TR/WCAG22/#resize-text).
   Текст не обрезается и не перекрывает другие элементы.
5. Переформатирование страницы при ширине области просмотра 320 CSS-пикселей по
   [критерию 1.4.10](https://www.w3.org/TR/WCAG22/#reflow).
   Основной текст читается без горизонтальной прокрутки;
   отдельные таблицы и блоки кода, требующие двумерного представления, могут прокручиваться внутри своего блока.
6. Контраст изменённых цветов и отсутствие сведений, переданных только цветом.

Запишите браузер, вспомогательную технологию и результат в PR.
Отмечайте только фактически выполненные проверки. Автоматический линтер Markdown не проверяет эти свойства.

## Применение к примерам

В первом запросе присутствуют условия, нумерованные шаги, ожидаемый статус и копируемый код.
В справочнике операции таблицы имеют заголовки, а ошибки сопровождаются действиями клиента.
Это проверка содержания по X01–X06, а не результат испытания экранным диктором.
Исходный ориентир: [WCAG 2.2 Quick Reference](https://www.w3.org/WAI/WCAG22/quickref/).
